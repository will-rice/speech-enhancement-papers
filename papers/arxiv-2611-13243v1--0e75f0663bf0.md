###### Abstract

We present GigaEdge Spench, an open-source SDK for streaming speech
enhancement on CPU servers, mobile devices, and in browsers.
Applications can build enhancement channels from neural denoising,
normalization and dynamics blocks, sample-rate conversion, and acoustic
echo cancellation where supported. These stages can be combined, while
normalization can also run without a neural model. The release includes
an 8 kHz INT8 denoiser and discriminative and hybrid 48 kHz FP32 models.
A shared C++ core supports ONNX Runtime and TensorFlow Lite through
native interfaces, Android and iOS SDKs, and WebAssembly integration.
Independent stream contexts share model resources, and consecutive
frames from one stream can be processed in a single inference call. We
evaluate the released models on EARS–WHAM v2 and compare their quality
and processing costs with RNNoise and DPDFNet2. All tested native and
Web configurations process files faster than real time, although larger
chunks require more time to collect input. We also measure how many
streams a shared model can process on a CPU. Our contribution is a
configurable deployment system and an experimental study of how model
choice, chunk size, and execution environment affect its use. All
reported SDK timing uses ONNX Runtime.

Keywords: speech enhancement, streaming inference, cross-platform
deployment, temporal frame grouping, computational efficiency

## 1 Introduction

Speech enhancement is an important component of voice communication and
speech interfaces. Neural approaches can improve the quality of noisy
recordings, while efficient implementations make local processing
practical \[1, 2, 3\]. However, a model used in a live application must
accept successive audio chunks and preserve its state while working with
an audio callback that may use a different block size. These
requirements also apply to the signal-processing stages outside the
neural graph, since the application depends on the complete audio path.

In this paper, we describe GigaEdge Spench, a software development kit
for building real-time audio enhancement pipelines on CPU servers and
end-user devices. The name Spench combines *Sp*eech, *En*hancement, and
*Ch*annel, where an enhancement channel is a configurable processing
pipeline. Applications can use normalization alone, neural denoising
alone, or both, and add acoustic echo cancellation where the platform
API supports it. The normalization stage can itself be built from
selectable signal-processing blocks. The shared core supports ONNX
Runtime and TensorFlow Lite through native, mobile, and browser
interfaces. We study this system, the quality of its released models,
and its processing costs in different execution environments. All
reported SDK performance measurements use ONNX Runtime, while the
external RNNoise reference uses its native C kernels.

The system has three main components. A shared C++ core handles
sample-rate conversion, spectral processing, and model state for each
stream, with C and C++ interfaces for its audio-processing modules.
Platform wrappers connect this core to Android, iOS, and Web Audio
applications and provide worker-based execution for live audio. The
open-source release also supplies three models for 8 kHz INT8 and 48 kHz
FP32 processing, although training, quantization, and conversion tools
are outside this SDK release. We study how chunk size and execution
environment affect processing cost, measure concurrent native
throughput, and evaluate all three models through the SDK CLI in
separate bandwidth conditions.

We developed the SDK for videoconferencing across native platforms and
browsers, where devices differ in compute resources and microphone
quality. Enhancement must share resources with video encoding and
decoding, including demanding codecs, while keeping audio free from
interruptions and other processing artifacts. These requirements shaped
the models’ quality/computation trade-offs. A high quality score alone
does not show whether a model fits such an application, because full
processing cost, buffering, and concurrent-stream capacity impose
different limits. We therefore examine three questions: how the released
models balance predicted quality and computation; how chunk size affects
native and Web processing; and how many independent streams can share a
model while each meets a processing-rate requirement.

Our contribution is a deployment design and an experimental study that
links model bandwidth, the number of consecutive frames in each
inference call, and the number of streams sharing model resources. We
combine these choices in configurable enhancement channels built on one
C++ core. The experiments show that larger chunks can provide more
throughput than adding CLI processes, and that the model with the lowest
arithmetic cost does not necessarily offer the best balance of quality
and measured capacity. We compare these choices with RNNoise and
sherpa-onnx/DPDFNet2, stating which operations and processing stages are
counted. Recurrent-state caching, model sharing, ring buffers, and
worker threads are established methods; our system contribution is their
integration and the study of the resulting deployment choices. The
detailed architecture and training objectives of the 48 kHz hybrid model
are outside this study’s scope.

## 2 Related work

### 2.1 Research software and efficient enhancement

Asteroid provides modular architectures and reproducible separation
recipes \[4\], while ESPnet-SE combines enhancement and separation with
ASR \[5\]. Both show how research software can be supported by benchmark
experiments. We focus on streaming in applications, where model
execution must work together with signal processing and host audio
interfaces.

RNNoise combines neural estimation with DSP and provides an inference
library, pretrained weights, feature-generation tools, and a training
procedure \[1, 7\]. It can also run in browsers: Jitsi’s RNNoise
WebAssembly wrapper includes a synchronous 0.2 build for AudioWorklet
use and an older asynchronous build \[8\]. We use the regular RNNoise
0.2 model as a strong native efficiency reference, while its WebAssembly
wrapper is outside our measurements. DTLN provides streaming inference
with externally managed recurrent state and ONNX/TensorFlow Lite
conversion \[2, 6\]. DeepFilterNet2 targets efficient full-band
processing \[3\], and later DeepFilterNet work provides real-time
enhancement with a public Rust implementation and deployment tools \[9,
10\]. GTCRN targets very low computational requirements \[11\]. DPDFNet
extends DeepFilterNet2 with dual-path recurrence \[12\]; its
implementation includes 8, 16, and 48 kHz models, stateful streaming,
and ONNX/TensorFlow Lite inference \[13\]. These systems provide a basis
for application deployment through efficient CPU inference,
recurrent-state caching, model export, and support for different
sampling rates.

### 2.2 Integrated audio processing and platform runtimes

WebRTC’s Audio Processing Module combines noise suppression, acoustic
echo cancellation, and automatic gain control \[14\]. SpeexDSP also
provides established audio-processing components, including a
preprocessor with noise suppression, residual echo suppression, gain
control, and VAD \[15\]. Our SDK follows this approach of combining
processing stages and uses SpeexDSP for echo cancellation.

sherpa-onnx is a relevant deployment reference because it offers C/C++
and other language interfaces for native, Android, iOS, and WebAssembly
environments, including streaming enhancement with GTCRN and
DPDFNet \[16, 17\]. It therefore already supports cross-platform neural
enhancement. We use its DPDFNet2 48 kHz HR configuration as an external
reference for quality and CPU capacity, with the shared-model adaptation
described in Section 5. Table 1 compares the focus of these systems
using their papers and official documentation as of October 2026.

### 2.3 Positioning and streaming validation

Compared with sherpa-onnx, we focus on how the enhancement pipeline is
organized. In the GTCRN and DPDFNet streaming implementations that we
inspected, each denoiser owns a model and one stream’s state, and
processes one spectral frame per neural call \[18\]. In GigaEdge Spench,
independent stream contexts share a model instance and its ONNX session,
so a new stream does not require a separate inference session. Our
released ONNX models also accept several consecutive frames in one call,
which allows larger chunks to change how inference is performed as well
as how audio is passed to the SDK. Sections 5 and 6 examine chunk-size
effects and shared-model capacity. For the capacity comparison, we adapt
sherpa-onnx to share a model and session across independent contexts as
well. Both measured configurations therefore share model resources, and
session duplication cannot explain their capacity difference. This API
comparison applies to the inspected enhancement implementations rather
than all speech-processing APIs in sherpa-onnx.

RNNoise already separates each stream’s denoising state from shared
weights. Its API provides independent DenoiseState objects that can use
the same loaded RNNModel; states using the default model also refer to
the compiled weight arrays \[19\]. Model/state separation is therefore
an established method. We combine it with model and backend selection,
temporal frame grouping, independent I/O rates, and configurable DSP
channels.

A second difference is the processing chain exposed to applications. The
public sherpa-onnx enhancement API configures the model and inference
settings, but does not expose a playback-reference AEC input or
configurable loudness-control stages \[20\]. Its streaming adapter
supports input resampling and returns audio at the model rate \[21\]. In
GigaEdge Spench, applications can combine neural denoising with selected
normalization blocks and, through native and Web interfaces, SpeexDSP
AEC. They can also choose the input and output rates independently for
neural enhancement. Normalization and denoising can run separately or
together, and applications can select the blocks within the
normalization stage. Table 2 shows the AEC limits of the mobile
interfaces.

Temporal caching is an established way to avoid recomputing history, as
used, for example, in streaming Wave-U-Net \[22\]. Each stream in our
implementation also retains its resamplers, spectral overlap, output
buffers, and statistics. Regression tests in the underlying product
compare sequential processing with larger and mixed-size chunks,
checking startup alignment and finalization within numerical tolerances.

## 3 System design

### 3.1 Enhancement channels and processing layers

The SDK and the three described models are publicly available in our
open-source GitHub repository.¹¹ 1
[https://github.com/salute-developers/gigadenoiser](https://github.com/salute-developers/gigadenoiser)

An enhancement channel is an ordered processing pipeline applied to an
audio stream. Here, channel refers to the pipeline rather than waveform
channel count, such as mono or stereo. Applications select the DSP and
neural stages and then choose the blocks within the normalization chain.
A normalization-only channel runs without loading a neural model, while
a denoising-only channel omits normalization. A combined channel uses
both, with the available stages and composition controls defined by the
platform API.

Figure 1 shows an example channel built from the shared C++ components.
The library provides DSP implementations and model-specific inference
adapters, while platform bindings connect them to host audio and manage
resource loading, initialization, and cleanup. This allows applications
to reuse the same processing code on different hosts and in different
channel configurations.

![](arxiv-2611-13243v1--0e75f0663bf0.figures/inline-1.svg)

Figure 1: An example enhancement channel. Stages can be omitted, while
normalization can itself combine selected DSP blocks. This is one
possible order; available stages and controls depend on the platform
interface. The neural stage uses ONNX Runtime or TensorFlow Lite
according to model and platform support (Table 2).

The released discriminative configurations use a 32 ms analysis window
and a 16 ms hop at model rates of 8 or 48 kHz. The corresponding
window/hop lengths are 256/128 and 1536/768 samples. Processing chunks
have durations $`T_{\mathrm{chunk}}=m\cdot 16`$ ms, where $`m`$ is a
positive integer within the implementation’s size limit. This gives
$`128m`$ samples at 8 kHz or $`768m`$ samples at 48 kHz. The ONNX
adapters pass the consecutive spectral frames of a chunk together along
the model’s temporal axis, so one inference call processes several
frames from the same stream while keeping that stream’s own recurrent
state. The chunk-size rule applies after resampling and buffering at the
model input; host audio callbacks may use different block sizes.

The built-in resampler allows input and output sampling rates to be set
independently of the model rate. When creating a stream context, the
application specifies both rates, and the SDK converts incoming audio to
the model rate before enhancement and the result to the requested output
rate. Since each context retains its resampler state, applications do
not need external sample-rate conversion. A higher output rate changes
the delivered format but does not extend the bandwidth processed by the
model.

### 3.2 Supplied models

The release includes three configurations: Spench 8 kHz INT8, Spench 48
kHz Discriminative, and Spench 48 kHz Hybrid. The first uses INT8
quantization, while the two 48 kHz ONNX models use FP32. Table 2 lists
backend support. We developed these models for devices and platforms
with different compute budgets, so both enhancement quality and
processing cost were design requirements. We evaluate them as model
choices within the same SDK.

Spench 48 kHz Hybrid combines a pretrained discriminative enhancer with
an additional generative component trained using a generative
adversarial network (GAN) procedure. During this training, the
discriminative model’s weights remain frozen. The term hybrid refers to
this combination, which we evaluate here as a released deployment
configuration.

The discriminative models are based on a modified FullSubNet
architecture \[23\]. In this paper, we focus on the SDK and the
interfaces used to run the released models in applications.

### 3.3 Stream-specific state

For the neural denoising stage and its associated resampling and
spectral processing, let $`x_{j,k}`$ denote the input to stream $`j`$ at
step $`k`$. We express this stateful operation as

```math
(\hat{s}_{j,k},z_{j,k+1})=\mathcal{P}_{\theta,c}(x_{j,k},z_{j,k}), \tag{1}
```

where $`\theta`$ denotes network parameters, $`c`$ the processing
configuration, and $`z`$ the state updated during processing. This state
includes recurrent tensors, convolutional histories, previous input and
spectral frames, resamplers, and running statistics. Each stream context
stores its own state, while the model adapter owns the shared inference
session, so adding a context does not create another session.

This separation prevents streams from changing each other’s history.
However, calls on the same context must not run concurrently, and
sharing a model does not imply a proportional increase in throughput.

### 4.2 Audio callbacks and workers

The host application and neural model may use different audio block
sizes. In the Android native processor and iOS audio-unit integration,
input and output ring buffers connect the audio callback to a dedicated
worker. While the worker processes complete chunks, the callback
transfers available samples. Android fills unavailable output with
zeros, and the iOS audio-unit documentation specifies silence while the
buffers are initially filled or the worker is delayed. These behaviors
affect the audio that the application receives.

The browser implementation connects an AudioWorklet to a worker through
messages or, where supported, shared memory. Shared-memory transport
requires browser support and cross-origin isolation. Neural processing
can therefore run separately from the audio callback, although
scheduling jitter remains possible and the design does not guarantee
hard real-time behavior.

The native C++ denoiser creates tasks and temporary buffers during
processing, so whether it can run safely in an audio callback depends on
the wrapper and how inference is scheduled.

### 4.3 Normalization and acoustic echo cancellation

Normalization is a configurable chain of level-control and dynamics
blocks. The C++ DSP interface adds these blocks to an ordered sequence
and allows each block’s parameters to be set independently. For example,
loudness control can be followed by a limiter or by a compressor and a
limiter. The chain can process audio alone or together with neural
denoising. These established tools help manage signal levels from
microphones of different quality.

Loudness control. This block adjusts the signal towards a target level
using smoothed gain and a maximum amplification limit. Its optional
speech-aware mode smooths RNNoise VAD estimates and updates loudness
statistics during detected speech \[1, 7\]. Normalization can also run
without VAD.

Automatic gain control. This block adjusts gain towards a target signal
power.

Peak-based range control. This block tracks the signal envelope and
adjusts gain towards a target peak level, with configurable attack,
release, and hold times.

Dynamic range compressor. This block reduces gain above a threshold
according to a configurable compression ratio, reducing the difference
between louder and quieter passages.

Noise gate. This block reduces the level of signal segments below a
threshold. Attack, release, and hold settings control its transitions.

Limiter. This block reduces gain at high signal levels to limit output
peaks according to a configured threshold.

Acoustic echo cancellation. This block uses SpeexDSP \[15\] version
1.2.1 and a playback-reference signal to reduce playback-related echo in
the microphone signal. The native and Web interfaces expose this
reference input, while the Android and iOS feature APIs do not.
Standalone normalization and AEC are SDK capabilities, but we do not
evaluate them as enhancement methods in this study.

### 4.4 Buffer adaptation

The browser tracks output-buffer refill events in a sliding time window.
If $`r_{k}`$ is the number of recent events including the current event,
the refill threshold in seconds is set to

```math
B_{k}=B_{\min}+\max(r_{k}-1,0)\Delta B. \tag{2}
```

The defaults are $`B_{\min}=64`$ ms, $`\Delta B=32`$ ms, a one-second
event window, and a low-performance notification at four recent refills.
The worker uses a 16 ms processing chunk by default. These settings
define the buffering policy rather than measured end-to-end latency. The
implementation also handles timeouts and feature switching.

A larger buffer reduces the risk of running out of output audio, but
adds delay and cannot prevent interruptions if processing remains slower
than the incoming stream. Buffer adaptation is an SDK feature; the
file-processing experiments below do not test playback continuity or
compare buffering policies.

## 5 Experimental setup

We study three deployment choices: the neural model, chunk size, and
concurrent stream count. We measure quality and processing cost within
the SDK and compare the results with regular RNNoise 0.2 and the
released DPDFNet2 checkpoint in its adapted sherpa-onnx deployment. Both
external models operate at 48 kHz, with an additional quality condition
for RNNoise output downsampled to 8 kHz. Normalization blocks and
acoustic echo cancellation are available for building channels but are
outside the experiments. SDK and sherpa-onnx performance tests use ONNX
Runtime, while RNNoise uses the unmodified native library and its own
inference kernels. The file-processing tests measure computation, rather
than end-to-end latency or playback interruptions.

### 5.1 Quality evaluation

We evaluated the discriminative and hybrid 48 kHz ONNX models on
EARS–WHAM v2 \[24, 25, 26\] through the SDK’s native CLI with 16 ms
chunks. The benchmark contains 886 matched noisy/clean file pairs, which
are also used in the separate 8 kHz condition. Input files for the two
48 kHz SDK models were sampled at the model rate, so no resampling was
needed. Normalization and acoustic echo cancellation were disabled.

The three released Spench models were trained on internal datasets
without EARS recordings, WHAM! recordings, or EARS–WHAM v2 mixtures.
EARS–WHAM v2 is therefore an external quality benchmark for Spench.
Since the released checkpoints have different training histories, their
quality can depend on training data, augmentation, and objectives as
well as architecture. Our comparison describes deployment choices rather
than isolating architecture or training method under a common training
setup.

All models in the 48 kHz comparison, including RNNoise and DPDFNet2, use
the same wideband PESQ protocol (PESQ-WB) \[27\]. We evaluate the 8 kHz
INT8 model on noisy audio downsampled to 8 kHz, using narrowband PESQ
(PESQ-NB) \[28\]. For an additional 8 kHz output reference, RNNoise
processes the original 48 kHz noisy recordings, after which its outputs
are downsampled to 8 kHz and compared with the corresponding clean
references using PESQ-NB. This compares two ways to produce 8 kHz audio,
although RNNoise has access to the original full-band input. It does not
test RNNoise on input already restricted to 8 kHz, and we report no
performance measurement for this output-downsampling path. Each model is
compared with noisy input at the corresponding sampling rate. PESQ-NB
and PESQ-WB scores are kept separate because they cannot be used to rank
models directly across bandwidths. Any sample-rate preparation within
the metric implementations is separate from SDK processing.

ESTOI estimates speech intelligibility \[29\], PESQ assesses perceptual
degradation against a clean reference, and SI-SDR measures
scale-invariant reconstruction of that reference \[30\]. For the 48 kHz
condition, we also use three families of non-intrusive MOS predictors,
which estimate human quality ratings from the evaluated waveform alone.
The predictor families serve different purposes, as described below.

DNSMOS: overall quality and the noise/speech balance. DNSMOS P.808
predicts overall recording quality and is our main overall measure
within this family \[31, 33\]. The separate P.835 predictor estimates
speech quality (SIG), background-noise quality (BAK), and overall
quality (OVRL) \[32\]. These outputs help show whether a gain comes from
a better predicted background or better predicted speech. BAK describes
perceived background quality rather than noise attenuation in dB, and
P.808 and P.835 OVRL are separate predictions.

SIGMOS: a broader view of signal impairments. SIGMOS predicts
P.804-based speech-signal quality (SIG), overall quality (OVRL), and
five dimensions: spectral/timbral coloration (COL), interruptions or
discontinuities (DISC), loudness (LOUD), noise (NOISE), and
reverberation (REVERB) \[34, 35\]. We use these dimensions to examine
possible effects of enhancement beyond its noise-related score.

NISQA: communication quality and distortion. NISQA was developed for
transmitted speech, including communication-network impairments \[36\].
It predicts overall MOS and four dimensions: Noisiness, Coloration,
Discontinuity, and Loudness. Along with another overall-quality
estimate, it helps identify predicted timbral changes, dropouts, and
unsuitable signal levels. The reported NISQA model has no separate
reverberation or speech-signal-quality output.

Higher values are better for every reported metric. Higher
Noisiness/NOISE/BAK scores mean a better predicted background, while
higher Loudness/LOUD scores mean more suitable loudness rather than a
louder signal. We keep the predictor families separate because they
differ in training and calibration, and do not average their outputs
into one MOS. Their dimensional scores are diagnostic predictions, not
direct measurements of physical artifacts.

For the full-band outputs, the reference DNSMOS implementation resamples
audio to 16 kHz, while SIGMOS operates at 48 kHz \[33, 35\]. NISQA v2
supports variable sampling rates \[36\].

Before computing reference-based metrics, we compensate for each
system’s output delay: 16 ms for Spench (128 samples at 8 kHz or 768 at
48 kHz), 20 ms for RNNoise 0.2 (160 samples for its downsampled 8 kHz
output or 960 at 48 kHz), and 40 ms for DPDFNet2 48 kHz HR (1920 samples
at 48 kHz). Noisy baselines need no compensation. This aligns enhanced
signals with their clean references and is separate from application
buffering or end-to-end latency.

Quality results are means across the benchmark files. Tables 3, 4, and 5
show these means, with bold values marking the highest scores at the
displayed precision and ties marked equally. We use two decimal places
and scaled units where needed. Bold type describes the results rather
than statistical significance. We consider the predictors together,
since a small numerical gap alone does not establish perceptual
equivalence.

We evaluate RNNoise 0.2 and the released dpdfnet2_48khz_hr checkpoint on
the same EARS–WHAM v2 files. The full-band comparison includes ESTOI,
PESQ-WB, SI-SDR, and all three MOS-prediction families. Table 5 places
the three overall predictions alongside weighted model arithmetic. This
compares the deployed checkpoints without isolating the effects of their
training procedures.

### 5.2 Model arithmetic and counting scope

We count one scalar multiply–accumulate as one MAC and report millions
of MAC per second of input audio (MMAC/audio-s). For ONNX models, we use
the executed convolution and matrix-product shapes, including grouped
convolutions and input/recurrent GRU or LSTM products. We exclude
biases, activations, normalization, elementwise recurrent gates,
quantization overhead, and external DSP. An INT8 or FP32
multiply–accumulate counts as one MAC, although its runtime cost depends
on the precision. We scale the per-step count by the actual internal
hop: 62.50 steps/s for the SDK models and 100 steps/s for DPDFNet2.

The ONNX profiler records executed weighted operations and checks that
instrumentation leaves model outputs unchanged. Profiling uses ONNX
1.19.1 and ONNX Runtime 1.23.2, while timing-test versions are given
separately. The Spench 8 kHz INT8 graph requires 397,688 weighted MAC
per 16 ms hop, or 24.86 MMAC/audio-s. The total for Spench 48 kHz Hybrid
is 1319.83 MMAC/audio-s, including forward Mel projections within the
graph. All comparisons in Table 5 include weighted projections within
the ONNX graphs.

For the released DPDFNet2 48 kHz HR graph, this convention gives
22,839,680 MAC per 10 ms hop, or 2283.97 MMAC/audio-s. We obtain the
same count for the sherpa-onnx release asset and the official Ceva
export. Published profiles list 2.42 GMAC \[13, 17\], which we report
separately from the common weighted-operator count used here.

We count RNNoise operations using the regular model in release 0.2
(model identifier 0b50c45). Its dense affine layers require 2,839,296
MAC per 10 ms frame, while the shipped implementation executes retained
$`8\times 4`$ weight blocks and separate recurrent diagonals \[37\].
Counting these products gives 1,073,280 MAC per active frame, or 107.33
MMAC/audio-s, compared with 283.93 for the dense equivalent. The sparse
count includes every product in a retained block, even if an individual
stored value is zero. It covers neural weighted products but excludes
FFT, pitch analysis, feature extraction, and other DSP. The unmodified
library may skip neural inference on detected silence \[19\]; our
arithmetic counts assume active frames, while capacity measurements keep
the library’s standard behavior on the common recording.

These counts use an explicit rule, but they do not give full pipeline
arithmetic or measured CPU operations. For example, they include Mel
projections within the SDK graphs, while RNNoise feature extraction is
outside its neural count. The complete-path timing below includes each
system’s signal-processing stages, so we assess speed from measurements
rather than MAC ratios alone.

### 5.3 Processing-time measures

For an input of duration $`D`$, SDK real-time factor is defined as

```math
\mathrm{RTF}_{\mathrm{SDK}}=\frac{\sum_{i}t_{i}+t_{\mathrm{final}}}{D}, \tag{3}
```

where $`t_{i}`$ is the processing time of call $`i`$ and
$`t_{\mathrm{final}}`$ is finalization time. Inference RTF uses total
neural inference time as the numerator. Loading, decoding, and
initialization are measured separately. Processing-time percentiles
describe the duration of SDK calls, not end-to-end audio latency.

### 5.4 Execution environment

The tests ran on an Intel Core Ultra 5 125H laptop with 32 GB of
installed RAM. The Linux environment exposed 18 logical CPUs and
approximately 15 GiB of RAM. It used Ubuntu 24.04.5 LTS under WSL2 (WSL
version 3.0.3.0, kernel 6.18.54.1-microsoft-standard-WSL2) on Windows 11
build 26300.9711, with Python 3.12.3 for the benchmark driver. The
measurements therefore describe this WSL2 environment rather than Linux
running directly on the hardware.

### 5.5 Concurrent CLI processes

To study how chunk size and process count affect total throughput, we
tested three models with 16, 64, and 128 ms chunks and 1, 2, 4, or 8
concurrent CLI processes, giving 36 configurations.

The C++ CLI loads a WAV file into memory once and creates a stream
context before a 60 s benchmark interval. It then processes the audio
continuously, returning to the start at the end of the file while
keeping the same context. Output is neither accumulated nor saved. Chunk
size sets the amount of audio passed to the SDK per call, while the
spectral-analysis hop remains 16 ms. A Python driver starts each group
of CLI processes together and waits for them to finish before the next
configuration. Each configuration was measured once.

Each worker measures SDK time per chunk and records accepted audio
samples, total processing time, RTF, and call-time percentiles.
Aggregate throughput is the total accepted audio duration divided by the
group’s elapsed wall time, including process startup and termination,
whereas worker RTF uses processing time alone. The benchmark also
records the maximum worker RTF and the largest of the workers’
individual p99 call times. The reported p99 is therefore not a
percentile computed from all calls, and neither it nor worker RTF gives
end-to-end audio latency.

The driver samples process RSS through /proc every 200 ms and records
the largest observed sum across CLI processes. This is the sampled peak
of the group sum, which can differ from the sum of individual process
peaks. It includes resident input audio and process overhead, may count
shared pages more than once, and may miss peaks between samples.
Per-process logs and launch parameters are saved with the aggregate
results.

### 5.6 Shared-model stream capacity

In a separate experiment, all streams run in one process and share model
resources, while each has its own processing context and OS worker
thread. SDK and sherpa-onnx contexts share an ONNX session; RNNoise
contexts share weights and use native kernels. Workers process a
repeated 20 s WAV as fast as possible with 16 ms input chunks. Each
measurement lasts 10 s, with model loading and context preparation
completed beforehand. Workers are pinned round-robin across available
CPUs, and CPU order is shuffled before each measurement. We allow 30 s
of rest between measurements and 3 min between full searches. This
measures capacity under the stated affinity policy and complements the
separate-process throughput experiment.

For $`P`$ concurrent streams, let $`D_{j}`$ be the duration in seconds
of audio processed by stream $`j`$ during the common interval $`T=10`$
s. We use wall-clock RTF,

```math
R_{j}^{\mathrm{wall}}=\frac{T}{D_{j}},\qquad R_{\max}^{\mathrm{wall}}=\max_{1\leq j\leq P}R_{j}^{\mathrm{wall}}. \tag{4}
```

An attempt passes if $`R_{\max}^{\mathrm{wall}}\leq 1`$, meaning that
every stream processes at least 10 s of audio within the common 10 s
window. Faster streams cannot compensate for a slower one. This measure
includes waiting and scheduling within the interval, whereas SDK-call
RTF counts processing calls. We accept a candidate stream count if any
of up to three attempts passes, stopping after the first success.

We perform three complete automated searches per configuration. In each
search, we select the successful measurement with the largest stream
count and keep the slowest stream’s wall RTF from that measurement. We
report the mean $`\pm`$ sample standard deviation of the three counts
and, separately, of their three RTFs. Since these RTFs come from
selected passing measurements, they are not independent confirmation
runs. The retry rule finds demonstrated passing counts but does not
guarantee repeated success at that count or that each chunk meets its
deadline.

The external capacity reference is sherpa-onnx 2.0.0 with
dpdfnet2_48khz_hr at 48 kHz. We adapt it to share one model and ONNX
session across independent stream contexts without changing the neural
network or signal-processing algorithms. It uses the same input WAV,
external chunk size, measurement window, acceptance rule, worker
placement, and rest intervals. Inference uses one internal thread.
Sherpa keeps its 10 ms internal hop and handles the 16 ms input chunks
through its standard adapter, while SDK models use a 16 ms hop. Equal
external chunks therefore do not imply equal numbers of inference calls.

RNNoise 0.2 uses the unmodified library and regular 48 kHz model, with
shared weights and an independent DenoiseState and worker for each
stream. We use the same 10 s windows, repeated 20 s input, 16 ms
external chunks, affinity policy, retries, and rest intervals. Loading
and warm-up finish before timing. Internally, RNNoise processes
480-sample (10 ms) frames, so the adapter retains residual samples
across 768-sample input chunks. Its API uses float samples on the 16-bit
PCM scale \[19\]. Timing covers the full library path, including
FFT/iFFT, features, and neural inference, and describes the native build
rather than the WebAssembly wrapper.

Before timing, Sherpa warms each context with three internal silence
hops and resets its state, while GigaEdge Spench warms the neural
network when loading the model. We keep each system’s runtime version
and settings: ONNX Runtime 1.28.2 for sherpa-onnx and 1.20.1 for
GigaEdge Spench. These versions match sherpa’s Linux x86-64 dependency
configuration \[38\] and the SDK dependency lockfile. We time full DSP
and neural processing in all three systems. The results compare deployed
configurations, so differences cannot be assigned to architecture, ONNX
Runtime version, or one implementation feature alone.

### 5.7 Single-stream CLI and Web measurements

To compare CLI and Web processing costs and the effect of chunk size, we
processed the same 30-minute mono WAV at 48 kHz in both environments.
Each model was tested with 16, 32, 64, and 128 ms chunks and three
independent repetitions per model/chunk/environment configuration,
giving 36 native and 36 browser runs. Runs processed the whole file as
fast as possible without saving output. These finite-file tests are
separate from the 60 s concurrent-process experiment.

Native execution used ONNX Runtime in Docker under Ubuntu 24.04.5 LTS in
WSL2, with a separate CLI process for each repetition. Browser execution
used headless Chromium 151.0.792.34 in the same Linux environment and a
Release build of the Web SDK with ONNX Runtime in WebAssembly. Each
repetition created a new browser instance, profile, model, and stream
context. Processing ran in a Worker without playback. Browser summaries
specify one inference-engine thread and 48 kHz input and output for
every model, so the 8 kHz model includes internal sample-rate
conversion.

We timed neural inference and complete processing calls separately.
Native SDK calls include resampling, spectral transforms, model
execution, and reconstruction; browser calls also include copying across
the JavaScript/WebAssembly boundary. Total SDK time includes
finalization. SDK RTF divides this total by input audio duration, while
inference RTF uses inference time instead. Both exclude loading,
decoding, resource acquisition, and initialization. We report medians
across three runs, and each displayed percentile is the median of the
three per-run percentiles rather than a percentile over all calls.
Separately computed medians need not sum to the median total time.

We measured CPU use during processing for the native CLI process and,
through a Linux cgroup, for all processes of the dedicated browser. CPU
percentage is total CPU time divided by elapsed measurement time and
multiplied by 100, so 100% means one fully occupied logical CPU. Native
measurements use processing-loop elapsed time, while browser
measurements use the cgroup monitoring interval. We sampled peak RSS
approximately every 200 ms for the native process and for the sum of
browser-process RSS. Browser RSS includes browser infrastructure and
input buffers, so it cannot be compared directly with native RSS as a
measure of model memory. Neither measurement isolates model weights, and
sampling may miss brief peaks.

We use CLI to denote native execution and Web to denote WebAssembly.
$`R_{\mathrm{inf}}`$ and $`R_{\mathrm{SDK}}`$ denote inference and
complete SDK RTF, respectively. $`p_{50}`$, $`p_{95}`$, and $`p_{99}`$
give processing-call times, and $`p_{99}^{\mathrm{inf}}`$ gives
inference-call time, all in milliseconds. For display, RTF columns use
$`100R`$ (percent of audio duration) so that small values remain
distinguishable with two decimal places; divide the entries by 100 to
recover RTF. Bold values mark the lowest inference and SDK RTF within
each model/path group.

For initialization time and resource use, we first take the median of
three repetitions at each chunk size and then report the minimum and
maximum across the four sizes. These ranges show differences between
configurations rather than uncertainty intervals. Native loading and
decoding were timed together, while Web file reading, decoding, PCM
preparation, and resource acquisition were timed separately.

We describe repeatability using the coefficient of variation (CV) of SDK
RTF for each model/chunk/environment configuration. CV is the sample
standard deviation across three runs divided by their mean.

### 6.2 Full-band quality and computation trade-offs

Table 5 relates the three overall predictions to model arithmetic.
Spench 48 kHz Hybrid scores higher than RNNoise 0.2 on all three overall
measures and on speech-signal quality, discontinuity, coloration, and
loudness. RNNoise 0.2 has better noise-related scores and a much lower
computation cost. Even on the same recordings, the choice therefore
depends on how an application balances noise suppression, speech
preservation, and available computation.

Compared with DPDFNet2 48 kHz HR, the hybrid model is competitive on
selected speech-quality dimensions. The DNSMOS OVRL gap is 0.05 and the
SIGMOS coloration gap is 0.07, while DNSMOS speech quality and SIGMOS
loudness favor Spench 48 kHz Hybrid. However, these close scores concern
individual aspects of the signal rather than overall quality
equivalence. DPDFNet2 48 kHz HR has higher reference-based scores and
all three overall predictions, including a 0.61 advantage in NISQA MOS
and clearly stronger noise-related scores. The hybrid is therefore close
on some speech-preservation measures, but remains behind in predicted
residual-noise and overall quality. We describe second-decimal
differences without assuming a fixed threshold for perceptual relevance.

The computation difference also needs to be considered with the quality
results. Spench 48 kHz Hybrid uses 1319.83 MMAC/audio-s versus 2283.97
for DPDFNet2 48 kHz HR, or 42.21% fewer counted weighted operations,
giving a ratio of 1.73. It therefore offers lower computation cost with
quality close to DPDFNet2 on selected speech dimensions, while DPDFNet2
retains stronger overall predictions. RNNoise has still lower sparse
arithmetic, although complete-path timing is needed to compare practical
processing costs.

This balance reflects the model’s intended use in videoconferencing on
native platforms and in browsers. Enhancement must provide useful speech
quality with limited processing delay while leaving resources for video
encoding and decoding, including demanding codecs. Lower model cost
helps meet these requirements across a wider range of devices, including
less powerful ones. The Web results in Table 8 show processing headroom
on the tested host. The higher cost of the sherpa-onnx/DPDFNet2 48 kHz
HR configuration is likely to leave less CPU headroom on weaker devices,
which may make continuous low-delay processing more difficult when video
workloads compete for resources. This is an expectation based on
processing cost, rather than a measured comparison of browser behavior
on those devices.

The shared-model results show the costs of bandwidth and quality
selection. Spench 8 kHz INT8 supports 593.33 passing streams on average,
compared with 151.00 for Spench 48 kHz Discriminative and 56.00 for
Spench 48 kHz Hybrid. Its capacity is therefore 3.93 times the
discriminative capacity and 10.60 times the hybrid capacity, although it
operates at a different bandwidth. Within the 48 kHz pair, the hybrid’s
quality gains come with a 62.91% reduction in passing stream count.
Model selection consequently affects service capacity as well as the
quality of a single stream.

Compared with the shared-model sherpa-onnx/DPDFNet2 48 kHz HR
deployment, Spench 48 kHz Discriminative and Spench 48 kHz Hybrid
support 10.07 and 3.73 times as many passing streams. The hybrid offers
a useful balance: some speech-quality predictions are close to DPDFNet2,
while its measured capacity is higher. Its 3.73-fold capacity ratio
exceeds the 1.73-fold weighted-arithmetic ratio, showing why arithmetic
alone cannot describe deployment efficiency. These ratios compare
complete configurations with different networks, DSP, internal hops, and
runtime versions; they cannot be interpreted as an SDK or
inference-engine speedup alone.

RNNoise 0.2 has the highest measured capacity at $`1088.67\pm 30.09`$
streams, or 7.21 and 19.44 times the counts of Spench 48 kHz
Discriminative and Spench 48 kHz Hybrid. Its native sparse execution and
combined DSP/neural design provide a strong low-cost reference. However,
the quality results show why throughput alone is insufficient for model
selection. All measured systems share model resources and keep stream
states independent, so model sharing by itself cannot explain this
ranking.

Taken together, quality and capacity results suggest three choices.
RNNoise 0.2 supports the most passing streams, Spench 48 kHz Hybrid uses
more computation for stronger predicted speech quality, and DPDFNet2 48
kHz HR has the strongest overall predictions with the lowest measured
capacity. These choices apply to the stated benchmark and timing
protocol. Since the search uses short windows, retries, and a fixed
affinity policy, its passing rates do not establish long-running service
limits or per-chunk deadline guarantees.

### 6.5 Native and browser processing costs

Tables 8 and 9 report single-stream processing costs, initialization
time, and resource use.

Larger chunks reduce inference and full SDK RTF for every model in both
CLI and Web execution, although the median call takes longer because it
processes more audio. Fewer calls may reduce fixed overhead, while
larger inputs may improve backend efficiency. Inference RTF also falls,
which means that the benefit comes from more than the application
wrapper. Larger chunks are therefore useful for throughput, provided
that a live application can allow the extra input-collection time.

Web processing is slower than native CLI processing in every matched
configuration, taking 1.79–3.27 times as much SDK time. This difference
includes backend and wrapper costs as well as WebAssembly execution. All
tested configurations still process audio faster than real time, and the
model ranking is the same in both paths. Applications therefore face a
similar choice between speed and model complexity in either environment.
At 128 ms, inference for the 8 kHz INT8 model takes about half of total
processing time or less, so further improvements must also address
resampling, spectral processing, reconstruction, and data handling.

Resource use does not follow processing speed directly. Web RSS is
similar across models with different inference costs because it also
includes the loaded recording and runtime overhead. Total application
memory therefore cannot be estimated from model size alone. The faster
model does not always have the lowest CPU percentage or initialization
time either. Since processing runs as fast as possible, CPU percentage
describes resource use during that work rather than the load needed for
a live stream.

Most configurations vary little between repetitions, although native
discriminative processing at 16 ms has a CV of about 27%. Its RTF ranges
from 0.04 to 0.06, with every run still faster than real time.
Comparisons involving that configuration are therefore less precise. The
measurements support the observed processing-cost trends, but do not
establish playback continuity or end-to-end latency.

Our applications use the SDK on devices with different processing
capabilities and microphone quality. Integration testing included
concurrent video streams, reflecting the videoconferencing workloads
that shaped the design. The released models balance speech quality
against the processing budget needed to keep audio running alongside
other tasks. These application checks provide practical experience,
while the file-processing benchmarks quantify headroom on the tested
host rather than playback interruptions or comparative browser stability
under video workloads.

## 7 Conclusion

We presented GigaEdge Spench, an open-source SDK that combines neural
denoising and configurable audio processing in reusable enhancement
channels. The release includes an 8 kHz INT8 model and discriminative
and hybrid 48 kHz FP32 models, together with selectable level-control
and dynamics blocks, independent input/output sample-rate conversion,
and SpeexDSP echo cancellation on supported interfaces. Applications can
use normalization alone, denoising alone, or both. Native interfaces,
Android and iOS SDKs, and Web execution use one C++ core, with ONNX
Runtime and TensorFlow Lite support as listed in the platform matrix.

Our system contribution combines these configurable channels with shared
model resources, independent stream contexts, and the ability to process
consecutive frames in one inference call. All tested native and Web
configurations process files faster than real time. With 16 ms chunks,
median complete SDK processing time is 0.65–9.89% of audio duration in
native execution and 1.42–24.38% in Web execution across the three
models. The larger hybrid model approaches DPDFNet2 48 kHz HR on
selected speech-quality predictions while supporting 3.73 times its
shared-model passing stream count, although DPDFNet2 retains stronger
overall-quality predictions. These results support a configurable
approach in which applications choose quality, bandwidth, and
computation together. Chunk-size effects and full-path costs show that
the choice also depends on how audio is processed. All reported SDK
timing uses ONNX Runtime.

The model trade-offs come from practical videoconferencing requirements
on devices with different hardware capabilities and microphone quality.
Enhancement has to leave room for demanding video codecs while limiting
audio delay and processing artifacts. Internal application tests with
concurrent video streams informed these choices and complement the
quantitative experiments, which cover one host environment and one
external quality benchmark. Regression tests check consistency across
chunk sizes, while runtime measurements show processing headroom rather
than per-chunk deadline guarantees. Human listening preferences,
long-duration service limits, and quantitative robustness across devices
and competing workloads remain to be studied. The public release
provides the SDK and model configurations for further work on these
deployment questions.
